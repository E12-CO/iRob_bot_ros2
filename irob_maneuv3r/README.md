# iRob_maneuv3r

```iRob_manuever``` is a collection of two position controllers for holonomic (a.k.a omnidirectional) robot. Which allows the robot to perform the complex maneuver such as simultaenous rotation during plannar movement (i.e. rotate while walking). The implemented controllers nodes in this package are :
- ```iRob_maneuv3r``` which is the simple PID based point A to point B position controller
- ```iRob_maneuv3r_tracker``` which is the feedforward omnidirectional pure-pursuit path tracking controller with the time to collision goal appraching technique. 

Both nodes **requires** the transform (tf2) broadcast between the map (or odom) frame to the robot base link frame (position tracking frame). Namespace system are supported in both node.

# ```iRob_maneuv3r``` node
## Related ROS topics
### Subscribed topics
- ```goal_pose``` to receive the message type ```geometry_msgs::msg::PoseStamped``` for the robot goal pose (pose = position and orientation).
- ```irob_cmd``` to receive the emergency "stop" message with the type ```irob_msgs::msg::IrobCmdMsg``` to cancel the goal. Use in emergency stop situation.
- ```/tf2``` to ```lookupTransfor()``` and get the current robot position and orientation.
### Published topics
- ```cmd_vel``` to publish the twist command with the message type ```geometry_msgs::msg::Twist``` .
- ```irob_stat``` to publish the goal status with the message type ```irob_cmd``` with the following status
    - **starting** -> indicates that the node received the goal pose.
    - **done** -> indicates that the robot reached the goal pose.
    - **failed** -> indicates the fatal transform lookup error. Possibly the SLAM node is dead or network error (DDS error).
    - **calceled** -> indicates that the node received emergency stop message.

## Parameter .yaml configurations
- ```map_frame_id``` select the frame name of the map. Default is ```map```.
- ```odom_frame_id``` is *optional* to select the frame name of robot odometry. Default is ```odom```.
- ```robot_frame_id``` is the position tracking frame, most of the time is set to ```base_link```. Default is ```base_ink```.
- ```use_odom_tf_only``` by default is set to ```false```. It is set to ```true``` when no transform from map to robot is available (i.e. you only have dead wheel encoder with no SLAM for example).
- ```walk_kp```, ```walk_ki``` and ```walk_kd``` is the P, I and D gain for the velocity controller PID. Start tuning ```walk_kp``` first to get a good speed/response. Then add a little ```walk_ki``` to solve the steady state error (the robot never truly reach the goal). Finally add the ```walk_kd``` by a little to help it response to sudden changes such as walking up the ramp or passing speed bump.
- ```walk_max_vel``` is the maximum speed that you allow the robot to move. Please leave some head room for torque to the robot can still walk and rotate. For example, if the robot can run in a  straight line with the max velocity of 1.5m/s. Set the ```walk_max_vel``` to 1.0m/s. And leaves the rest 0.5m/s as a head room for the robot to rotate.
- ```walk_vel_filter``` is the velocity command filter. Recommended to set it to ```1.0``` first to tune the PID controller. Then adjust it to lower value like 0.9, 0.8 or 0.7 until the robot motion is smooth but not to slow.
- ```walk_goal_tolerance``` is set to a distance (radius) from the goal point. If the robot enters into this radius. It will consider that it reaches the goal. Good PID tuning and low noise SLAM tuning can achieve 15 mm (0.015m) precision with Hokuyo lidar (acoording to Tokyo RoboTech team).
- ```rotate_kp```, ```rotate_ki``` and ```rotate_kd``` is the P, I and D gain for the rotation (orientation) controller PID. Tuning methodology is the same as the ```walk_kp/ki/kd```.
- ```rotate_max_vel``` is the max rotation speed of the robot in rad/s unit. Generally, this would set by a trial and error process. And you need to make sure that the maximum rotational speed won't degrade (steal) the linear velocity set by the ```walk_max_vel```. 
- ```rotate_goal_tolerance``` is also the same concept like the ```walk_goal_tolearance```. Except that it's in radiant angle. How mucht you expect the robot getting close to the goal pose orientation and consider it at "reached the goal".

# ```iRob_maneuv3r_tracker``` node
## Related ROS topics
### Subscribed topics
- ```path``` to receive the message type ```nav_msgs::msg::Path``` containing a collection (an array) of poses generated by the ```iRob_trajectory_maker``` python node.
- ```irob_cmd``` to receive the emergency "stop" message with the type ```irob_msgs::msg::IrobCmdMsg``` to cancel the goal. Use in emergency stop situation.
- ```/tf2``` to ```lookupTransfor()``` and get the current robot position and orientation.
### Published topics
- ```cmd_vel``` to publish the twist command with the message type ```geometry_msgs::msg::Twist``` .
- ```irob_stat``` to publish the goal status with the message type ```irob_cmd``` with the following status
    - **starting** -> indicates that the node received the goal pose.
    - **done** -> indicates that the robot reached the goal pose.
    - **failed** -> indicates the fatal transform lookup error. Possibly the SLAM node is dead or network error (DDS error).
    - **calceled** -> indicates that the node received emergency stop message.
- ```carrot``` to visualize the pure-pursuit lookahead point "carrot" in rViz, with the message type ```visualization_msgs::msg::Marker```
- ```vel_vector``` to visualize the velocity and heading command in rViz, with the message type ```visualization_msgs::msg::Marker```. The arrow length represents the velocity (e.g. 1m arraw = 1m/s velocity).

## Parameter .yaml configurations
- ```map_frame_id``` select the frame name of the map. Default is ```map```.
- ```odom_frame_id``` is *optional* to select the frame name of robot odometry. Default is ```odom```.
- ```robot_frame_id``` is the position tracking frame, most of the time is set to ```base_link```. Default is ```base_ink```.
- ```use_odom_tf_only``` by default is set to ```false```. It is set to ```true``` when no transform from map to robot is available (i.e. you only have dead wheel encoder with no SLAM for example).
- ```walk_max_accel``` is the maximum linear acceleration of the robot in the m/s^2 unit. This can be obtained from driving the robot start from 0m/s to it's max velocity and use something like tape measure and slow-mo video to determine the acceleration.
- ```walk_max_vel``` is the maximum speed that you allow the robot to move. Please leave some head room for torque to the robot can still walk and rotate. For example, if the robot can run in a straight line with the max velocity of 1.5m/s. Set the ```walk_max_vel``` to 1.0m/s. And leaves the rest 0.5m/s as a head room for the robot to rotate.
- ```walk_min_vel``` is the minimum speed that robot can move. This ensures that when the robot is maneuvering the curve. The robot is still moving. **DON'T** set it to zero. At least 0.1 m/s is fine. But if you are confident in the tire grip or the robot is "โหลดต่ำ" (i.e. low COG). You can set it to 0.4m/s to improve the cornering speed.
- ```brake_max_devel``` is the maximum deceleration rate in m/s^2 which determine how hard your robot brakes when approaching the goal pose. Recommend setting it x2 the ```walk_max_accel```.
- ```lookahead_distance``` is the distance that the robot look forward for the next point to track. Shorter lookahead distance allows the robot to follow the path closely but the robot need to be slow. Longer lookahead distance allows the robot to follow the path very fast but not precise. Setting to 0.6 m seems to be good for 1m/s robot. 2m/s robot might need to set 1m lookahead distance.
- ```lookahead_ff_points``` or "lookahead feedforward points" is how many future pose point that robot will look for in order to prepare for the sharp turn, curve slowdown. Faster robot need more ```lookahead_ff_points```. This also depends on the point per distance density provided in the ```path``` topic. By default, 8 lookahead point is good enough for 1m/s robot.
- ```rotate_kp```, ```rotate_ki``` and ```rotate_kd``` is the P, I and D gain for the rotation (orientation) controller PID. Tuning methodology is the same as the ```walk_kp/ki/kd``` in the ```iRob_maneuv3r``` PID node.
- ```rotate_max_vel``` is the max rotation speed of the robot in rad/s unit. Generally, this would set by a trial and error process. And you need to make sure that the maximum rotational speed won't degrade (steal) the linear velocity set by the ```walk_max_vel```.
- ```walk_goal_tolerance``` is set to a distance (radius) from the goal point. If the robot enters into this radius. It will consider that it reaches the goal. Good PID tuning and low noise SLAM tuning can achieve 15 mm (0.015m) precision with Hokuyo lidar (acoording to Tokyo RoboTech team).
- ```rotate_goal_tolerance``` is also the same concept like the ```walk_goal_tolearance```. Except that it's in radiant angle. How mucht you expect the robot getting close to the goal pose orientation and consider it at "reached the goal".
